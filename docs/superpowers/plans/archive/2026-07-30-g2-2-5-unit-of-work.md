# G2.2.5 — Unit of Work para mutações financeiras compostas — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tornar atômicas as mutações compostas de payable, fatura/compra, recorrência e contribuição de goal nos adapters canônico e legacy.

**Architecture:** Reutilizar `withTransaction(pool, callback)` e o `AsyncLocalStorage` já existente. Cada método composto executará validação, efeitos, recálculo e leitura final com o mesmo `PoolClient`; a rota de payable com template ganhará um comando de store único.

**Tech Stack:** TypeScript, Fastify, PostgreSQL/`pg`, Vitest, pnpm workspaces.

**Agent Orchestration:** Single-Agent Looped — os adapters compartilham estado e conexão; cada etapa será RED → GREEN → verificação.

### Task 2: Implement canonical Payable Unit of Work

**Files:**
- Modify: `apps/api/src/payables/postgres.ts`
- Modify: `apps/api/src/payables/in-memory.ts`

- [ ] **Step 1: Add client-scoped query helpers.**

Use `withTransaction(pool, async (client) => { ... })` and route all statements in the callback through `client.query`. Do not call the existing pool-level `query` helper from a compound callback.

- [ ] **Step 2: Move canonical `markPayablePaid` into one transaction.**

The callback must execute in this order: lock/read payable by household, update payable, insert optional transaction, create next recurring payable when due, link `paid_transaction_id`, select the final payable. Any thrown error must escape the callback.

- [ ] **Step 3: Move canonical `undoPayablePayment` into one transaction.**

Read payable, update payable status/payment columns, soft-delete the linked transaction when present, and select the final payable using the same client.

- [ ] **Step 4: Add `createPayableWithTemplate`.**

Insert payable and optional template in one callback, then select and map the payable. A template failure must roll back the payable. Implement the in-memory method by validating both inputs before pushing either object; then push both objects.

- [ ] **Step 5: Run canonical route/store tests.**

```bash
pnpm --filter pi-finance-api exec vitest run tests/routes/payables.test.ts tests/contract/unit-of-work.test.ts
```

Expected: PASS.

### Task 3: Implement canonical card and goal Unit of Work

**Files:**
- Modify: `apps/api/src/cards/postgres.ts`
- Modify: `apps/api/src/goals/postgres.ts`

- [ ] **Step 1: Wrap canonical `createCardPurchase`.**

Inside one `withTransaction` callback, validate category/account, find-or-create the statement, insert the transaction, recalculate total/status, and return the created transaction. Replace every callback-internal `query(...)` with `client.query(...)`.

- [ ] **Step 2: Wrap canonical `createRecurringPurchase`.**

Perform reference validation and recurring row insertion in one `withTransaction` callback. The returned row must be mapped from the same transaction result.

- [ ] **Step 3: Wrap canonical `updatePurchase`.**

Use one client for transaction lookup/update, statement total/status recalculation, and final statement detail. Add a client-scoped statement-detail helper or return the final detail from client queries; do not call `this.getStatementDetail` from inside the transaction because it uses `pool.query`.

- [ ] **Step 4: Wrap canonical `updateCard` and `contributeToGoal`.**

Wrap the canonical credit-card account update in `withTransaction(pool, async (client) => ...)`, use `client.query`, and return the mapped row from the transaction. Then wrap canonical `contributeToGoal` so the goal update and contribution insert share that client.

Read the goal with household scope, update accumulated amount/status, insert `goal_contributions`, and return the contribution inside one `withTransaction` callback.

- [ ] **Step 5: Add focused tests for each successful Unit of Work.**

Assert the existing route behavior remains unchanged and that the methods issue one transaction boundary when used with a fake pool.

