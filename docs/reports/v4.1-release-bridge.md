## 3. Opções de bridge (decisão humana)

### Opção A — V4 primeiro, V4.1 depois (2 promoções)
1. Promover V4 (`ce787e4`/`dd10e2b`): backup → migrate-job (V053/V054) → API → smoke (health, login cookie-first, device token rotate, `/client-events`) → PWA → Agent → smoke E2E read-only → observação 48h.
2. Implementar V4.1 sobre produção já V4; promover em releases por fase.
- **Pró:** rollback por etapa; blast radius menor por release; janela compat V3↔V4 já desenhada (ADR-015).
- **Contra:** 2 janelas de deploy; risco V4 descoberto tarde.

### Opção B — V3 → V4.1 direto (1 promoção composta)
1. Implementar V4.1; promover tudo de uma vez: backup → migrations (V053/V054 + V4.1) → API → PWA → Agent → smoke composto → reconciliação.
- **Pró:** 1 janela.
- **Contra:** release composta de alto risco (muitas mudanças de sessão/auth/financeiro simultâneas); rollback só para o estado V3; debugging de regressão ambíguo (V4 vs V4.1). **Contraria o espírito do release-bridge gate (§3.3).**

**Recomendação técnica: Opção A.** V4 já tem plano de smoke/rollback e gates verdes locais; separar V4.1 preserva reversibilidade. Decisão final: humana (plano §3.3), com inventário, smoke e rollback por etapa.
