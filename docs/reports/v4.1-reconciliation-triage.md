## 2. Por que estes grupos existem (hipótese de causa-raiz)

- **statement_total / statement_payment:** o invariante legacy é que o total da
  fatura deriva de `SUM(transactions WHERE statement_id)` — `cards/legacy-postgres.ts:174`
  (`recomputeTotal`) e query de reconciliação em `sql.ts:111-125`. Os 8 statements
  têm `linked_count=0`: nenhuma transação carrega seu `statement_id` (inserções
  antigas sem vínculo ou transações apagadas historicamente). Sem lock histórico
  (Fase 0), os totais armazenados divergiram do ledger — exatamente o antecipado.
- **orphan_card_purchase (47):** linhas de `card_purchases` com `transaction_id`
  NULL, i.e. criadas antes do vínculo transação-compra (pré-V033). O check
  `card_purchase` está limpo (0/47) **por desenho**: `detectors.ts:412-413`
  ignora linhas sem `txId` — não é sinal de saúde, é lacuna de cobertura que este
  grupo preenche. Query de detecção: `sql.ts:304-315`.
- **payable_payment (2):** payables com `status='paid'` cujo `paid_transaction_id`
  aponta para transação com `deleted_at` preenchido (detector `detectors.ts:330-345`).
  Hipótese: transação de pagamento excluída (soft-delete) manualmente no histórico.
- **accounts_balance (1):** conta `814332c4` com saldo armazenado −56000
  (−R$ 560,00). O detector legacy (`detectors.ts:164-221`, base `sql.ts:90-108`)
  só emite `negative_stored_balance` sem `expected` quando o armazenado **confere**
  com o derivado (ou não há base inicial) — ou seja, o ledger sustenta o negativo.
  V4.1/D1 proíbe saldo negativo para escritas novas; este estado é anterior.
- **statement_payment:** `status_mismatch` = `paid` com `paid_cents=0`
  (`detectors.ts:293-305`, terceiro ramo); `payment_coverage_gap` = soma paga dos
  statements do ciclo sem transação `expense` de descrição `Pagamento fatura <ciclo>`
  (`sql.ts:139-157`, `detectors.ts:307-319`). Hipótese: pagamentos registrados sob
  outra descrição/convenção, ou faturas marcadas `paid` sem baixa real.

### 4.1 statement_total — recomputação (proposta condicional)

Verificação obrigatória por statement (ex. `0478c43b-…`, actual 462850):

```sql
-- 1. Confirma que não há ledger vinculado:
SELECT COALESCE(SUM(amount_cents),0), COUNT(*)
  FROM transactions WHERE statement_id = '<stmt_id>' AND deleted_at IS NULL;
-- 2. Confirma que não há compras órfãs sustentando o total armazenado:
SELECT COALESCE(SUM(amount_cents),0), COUNT(*)
  FROM card_purchases WHERE statement_id = '<stmt_id>' AND deleted_at IS NULL;
```

- Se (1) = 0 **e** (2) = 0 → **Classe A**: zerar o total é regeneração de projeção
  a partir do ledger autoritativo (§17.1, exemplo aceitável):
  `UPDATE statements SET total_cents = 0 …` (+ revisar `status`/`paid_cents`).
- Se (2) > 0 → **Classe B**: o total armazenado pode ser o único registro do valor
  real da fatura; zerar destruiria informação. Relink das compras primeiro (§4.4),
  depois recomputar via `recomputeTotal`.
